# بنية MARINE 360

## التقنيات الحالية

React 19، TypeScript، TanStack Start/Router، Vite 8، Tailwind CSS 4، Leaflet مع تدوير الخريطة، وThree.js للمجسم. ناتج الإنتاج يستخدم Nitro؛ البناء العادي يبقي إعداد Vercel، و`build:render` ينتج خادم Node.js مستقلًا لـRender.

## حدود البيانات

اسم السفينة والموافقة والثيم تُحفظ في localStorage. لا تفترض حفظ المسارات أو حالة الأجهزة بعد إعادة تحميل الصفحة؛ أبقي السلوك الأصلي. وحدات قاعدة البيانات الموروثة تستخدم PGlite في الذاكرة عند غياب `DATABASE_URL`، ولا تعني وجود تخزين ملاحي دائم.

مصادر الشبكة موجودة كما في الأصل: Esri وOpenSeaMap لطبقات الخرائط، VesselFinder وOpen Waters للأهداف، Open-Meteo للطقس والبحر، صفحة مدّ أم قصر، ومصدر NAVAREA IX لـNAVTEX. توفر هذه المصادر وتغيّر صيغها يقعان خارج اختبارات الحسابات المحلية.

## خطوات التطوير التالية

1. ثبّت خط التحقق الحالي باستخدام `npm run check` واختبار الواجهة قبل كل تعديل ملاحي.
2. استخرج تدريجيًا وحدات الأجهزة والخريطة والمجسم والمسارات من `survey-explorer.tsx`، كل مرة مع الحفاظ على السلوك واختبارها. الملف يتجاوز أربعة آلاف سطر، وإعادة هيكلته كاملة أثناء التجهيز تزيد نطاق المخاطرة.
3. أضف اختبارات بيانات مسجلة من أجهزة JRC وDGPS وJFE الفعلية بعد توفيرها، بما فيها انقطاع الاتصال وإعادة الربط.
4. أضف اختبارات عقود للخدمات الخارجية باستخدام عينات ثابتة، ثم timeouts وسياسات إعادة محاولة واضحة. الجلب الخادمي لـAIS والمدّ وبعض المصادر لا يحدد مهلة تطبيق صريحة حاليًا.
5. إذا لزم حفظ المسارات أو الحسابات، صمّم التخزين والمصادقة كميزة مستقلة؛ وحدات Grok السابقة تتطلب إعداد خدماتها ومساراتها ومراجعة callback URLs قبل تفعيلها. تحديث Better Auth الحالي يستخدم `signIn.social` و`/api/auth/callback/<providerId>`، وتسجيل الدخول الفعلي لم يُختبر في هذا التجهيز.
